# Workout Suite architecture

Workout Suite is a local-first strength-training tracker with a separate scientific analytics companion. Mobile logging uses SQLite offline; files carry data between the Expo app and Python companion. Cloud sync, Supabase, social leaderboards, and remote coach writes are historical proposals, not current execution paths.

## Subsystems and dependency direction

| Subsystem | Responsibility and boundary |
| --- | --- |
| `mobile/src/features/`, `context/` | React Native screens, navigation, and repository injection. `mobile/App.tsx` composes repositories and the root UI. |
| `mobile/src/ui/` | Shared palette, spacing, shapes, common control styles, SVG icons, tab bar, screen headers, and badges. Depends on React Native and the existing SVG integration; contains no repository or training logic. Feature screens consume these components and tokens. |
| `mobile/src/services/` | Application use cases: session lifecycle, imports/exports, substitutions, workload analysis, program evolution, and device integrations. Services use repository ports and core logic. |
| `mobile/src/core/` | Shared TypeScript entities, deterministic math, parsers, program generation, and progression rules. Keep calculations independent of React Native and SQLite. |
| `mobile/src/domain/repositories/` | Persistence interfaces consumed by services and screens. |
| `mobile/src/database/` | SQLite connection, schema/migrations, seeds, concrete adapters, and in-memory test adapters implementing the ports. |
| `schemas/` | JSON contracts for workout exports and calibrated parameters, plus a shared example fixture. |
| `companion/src/ingestion/` | Pydantic validation of transferred workout data. |
| `companion/src/models/`, `analysis/` | Adaptive Kalman strength estimation, Banister fatigue/readiness, recovery, mesocycle analysis, hypertrophy signals, volume landmarks, and SFR evaluation. |
| `companion/src/export/` | Calibration orchestration and serialized parameter output. |
| `companion/src/ui/` | Streamlit application and Plotly chart builders; consumes ingestion, analysis, models, and exports. |

Dependency intent: presentation calls services/models; services call core calculations and repository interfaces; SQLite and in-memory adapters implement those interfaces. `App.tsx` is the mobile composition root. Avoid SQL in screens and framework dependencies in domain math. These boundaries are conventions, not checks enforced by a dedicated architecture linter. The Python models depend on scientific libraries and Pydantic; they are not dependency-free.

## Primary execution flows

1. **Startup and logging:** Expo starts through `mobile/index.ts` and `mobile/App.tsx`; database initialization applies migrations and seeds. Repository context exposes adapters to screens. `WorkoutTabRouter` resolves an active session, a program template, or an empty state. `ActiveSessionService` persists set edits and completion through repositories. Crash recovery can resume or discard interrupted workouts. Warm-up adjustment, progression, and rest timing run through services and core rules.
2. **Programs:** profile/questionnaire input feeds `synthesizeProgram`; `candidateScorer` ranks exercises using biomechanical and preference constraints. Initial set defaults are starting prescriptions, not effective-rep equivalences. Repositories persist templates, exercises and LP/DP/DDP/capacity rules. `trainingAdaptation.ts` and `TrainingAdaptationService` own the automatic session policy: durable prescription snapshots make effort/load/rep comparisons explicit, while program state tracks misses, recovery sessions, pain returns and next-block adjustments. Home, Workout preflight and template startup share `buildWorkoutPreview`, including personalized load prediction and recovery overrides. Strength level can update from recent eligible local sets while retaining the companion's exercise-specific curve shape; prediction supports 1–10 reps at 0–4 RIR and easier recovery prescriptions, independently of learning eligibility. The logger requires a final working-set effort rating and runs adaptation at completion. Ordinary plateaus wait for the next block; repeated deterioration across eligible movements triggers easier-effort recovery for one week's session count. Pain 7–10 ends remaining exercise sets immediately, followed by a lighter return and substitution if discomfort persists. `ProgramEvolutionService` automatically reviews completed blocks, preserves productive work and IDs/rules, applies justified changes with mood/preferences, and returns explanations of actual changes. Runtime previews suppress legacy immediate reset rules. Block length starts at four weeks and only changes with qualified companion evidence; days and time preferences are not changed. See [training evolution policy](TRAINING_EVOLUTION.md) for thresholds and fallbacks.
3. **Import/export:** `ImportService` parses supported external logs and persists matched workouts/body metrics. `ExportService` serializes SQLite data to the workout export contract and uses Expo file/sharing APIs. Companion validates the transferred JSON with `WorkoutExportPayload`.
4. **Analysis:** `companion/src/ui/app.py` loads workout data; model and analysis modules derive strength/endurance, fatigue/readiness, recovery, mesocycle recommendations, landmarks, and audits. Plotly builders render the results. Tier 1 mobile strength calculations are immediate heuristics; Tier 2 companion estimates use longitudinal adaptive models.
5. **Calibration round trip:** `param_exporter.py` builds calibrated parameter JSON, including actual strength histories for mesocycle analysis and a typed `mesocycle_feedback` evidence object. Mobile `CalibratedParamService` validates/imports curves and feedback into local persistence; `ProgramEvolutionService` checks age, goal, history, confidence and exposure-level effort coverage before considering a length change. Legacy files without feedback retain block length. This transfer is file-based, with no background cloud synchronization.

## Persistence, configuration, and integrations

Discarding a session permanently deletes its workout and sets through the repository deletion path. Both normal logging and crash recovery use `workoutDiscardService`; its returned discarded snapshot is only a receipt, never a persisted session. Startup removes discarded records retained by older versions. Completed sessions are protected from the discard operation and remain deletable through history. Calendar excludes discarded records, scrolls the grid and agenda in one vertical container, and rechecks session status before opening: completed sessions open details; only in-progress sessions can resume in the logger.

Mobile navigation separates recent training from athlete setup. Home uses `loadTrainingOverview` for rolling local-calendar 7/14-day windows, comparisons, completed-session drill-downs, and rep PRs against earlier completed sessions with matching equipment. The period preference is stored in user settings. Home and Workout preflight share next-template selection and resolved plans through `workoutPreviewService` and `WorkoutPrescription`. The plan combines template targets, matching-equipment working loads, and progression results; startup populates those same working sets. Effective progression loads are converted to entered loads using exercise/gear multipliers and bodyweight (settings, or inferred from prior system load). Compact summaries show sets, rep targets, load, and effort; differing loads use comma-separated sets, unknown loads use a dash, and bodyweight/assistance are explicit. Supersets render together, including across Home's preview limit. Progression reasoning is available by tapping an exercise. Earned rule-based increases are applied automatically in the next template startup, taking precedence over estimated starting loads while pain/recovery overrides remain authoritative. The logger does not offer accept/dismiss progression prompts. After completion and adaptation, `captureWorkoutProgression` saves next-workout load increases in the workout-specific `training_progression_summary_<workoutId>` user setting before block evolution; the completed session summary reads this saved result rather than recomputing it from later history. `normalizeExerciseGroups` requires two distinct exercises per superset in generation and read/display paths, so legacy orphan group IDs render as ordinary exercises. Program management is accessible from Workout, Home, and Profile through the root program hub without unmounting an active logger. Profile provides an Exercises list linking directly to exercise details/records/history, plus SBD/DOTS, gear, and body-metric destinations plus separate editors for training preferences, personal details, and equipment access. `mergeProfileEditorChanges` preserves unrelated profile fields and stages training changes for the next cycle. SBD history uses running best lift estimates and bodyweight recorded on or before each session; estimated totals/DOTS are labeled separately from tested or competition results.

SQLite is the mobile source of truth, including active workouts. Keep canonical loads in kilograms and convert at presentation boundaries; preserve raw versus effective load semantics for gear, per-hand, assisted, and bodyweight exercises. Schema DDL and versioned migrations live in `mobile/src/database/schema.ts`; defaults live in `database/seeds/`. Types live in `core/types/index.ts`; persistence ports live in `domain/repositories/`.

Training objectives are strength, hypertrophy, endurance and longevity; mood is independent. `core/rules/trainingGoals.ts` normalizes legacy powerbuilding profiles to strength primary plus hypertrophy secondary, or expands a legacy secondary entry relative to the existing primary goal. Profile repository boundaries, generation and export share this rule; companion ingestion mirrors it for older files. Reads preserve mood and saved workouts; subsequent profile saves/new exports use canonical goals. The workout wire schema continues accepting legacy goal strings for compatibility.

`programVolumePlanner.ts` allocates experience-based weekly starting targets independently of mood and reserves direct arms/core. Advanced defaults target 16 chest/back/quad sets, 14 hamstring/delt/glute sets, 12 direct biceps/triceps sets, 10 calf sets and 8 core sets per week. These are starting policy defaults, not universal biological thresholds. Fury distributes work above three sets into compatible complementary variations where the catalog/preferences permit, preserving designated main strength work. Other moods can add variations when a single exposure's five-set limit would prevent meeting the weekly target. Pruning compares weekly coverage and preserves a represented stimulus rather than cutting by list position.

Get Out prioritizes its time budget: eligible press/pull and accessory antagonists can be paired, including unequal rounds; unpaired suitable movements can use explicit myo/DC. High axial loading, squats and hinges are excluded from both dense pairing and rest-pause conversion; strength compound recovery remains protected. A newly generated Get Out plan is rejected if the scheduling model still exceeds the requested limit. Other goals expose remaining time conflicts. Volume shortfalls remain visible rather than increasing the user's days/time preference.

`sessionPlanning.ts` supplies one estimator for generation/evolution including setup, ramp-up, reps, unilateral work, rounds and every mini-set/rest. Optional `TemplateExercise.rest_seconds` and `rest_pause` are persisted by SQLite v12 (`rest_pause_json`), cloned/exported and mirrored in the companion schema. Preview/startup expand each activation into working + mini rows at one load; logger timers apply the prescribed short rest after the activation and mini-sets. Progression uses activation sets; adaptation compares each phase against its own rep target and includes the protocol in exposure comparability. Recovery/pain-return previews suppress clusters. Full/activation sets, mini-sets and estimated stimulating reps are reported separately; compressed-dose estimates are uncertain heuristics, not fixed set equivalences. Evolution explains execution changes and remaining conflicts. Personal muscle emphasis and recovery-preserving easy back fillers remain future work; see the [goal-aware generation analysis](implementation_plans/Goal_aware_program_generation_analysis.md).

Smart Warmup is disabled until enabled within the Automated Warm-Up Sets card in Settings; its assessment toggle is independent of the generation mode. The mounted logger reloads this preference on tab activation. When enabled, completing the last warm-up offers a reviewed load suggestion; preview and application use the same planned load and core calculation. Normal assessments preserve all remaining prescribed loads. Quantization cannot move a suggestion outside the -10%/+5% limits; when no load step fits, the plan is maintained and the UI explains why. Displayed percentages describe the actual rounded change.

Automatic warm-up generation follows one eligibility policy for template startup and exercises added during logging: Smart Compounds uses the exercise's compound flag, All Lifts includes isolation exercises, and Manual Only lets users create warm-ups with Add Set and change the set-type tag to Warm; there is no per-exercise generation button. The logger refreshes the mode on tab activation. Warm-up shortening uses completed working sets supplied by the logger or explicit warmed-muscle context; merely populating a template does not count as training. Set-row swipe gestures reveal a Delete action that uses the existing session-service deletion path. Superset auto-navigation skips finished exercises and stays put when no partner has remaining work.

Mobile configuration is in `mobile/app.json`, `package.json`, `tsconfig.json`, and `jest.config.js`. Expo adapters provide SQLite, document selection, files/sharing, haptics, and notifications. Companion dependencies and pytest/mypy settings live in `companion/pyproject.toml`, with runtime dependencies also in `requirements.txt`. Use only its local `.venv`.

Exchange changes must synchronize mobile payload/types, `schemas/*.schema.json`, and companion Pydantic models. The mobile export test writes the shared fixture; Python then validates it against both JSON Schema and Pydantic. Run those checks in that order. There is currently no repository CI workflow, dedicated ESLint configuration, or configured native production build script.

## Extension and validation

Mobile UI changes should extend the shared `ui/theme.ts` tokens and `ScreenHeader`, `Badge`, `AppIcon`, and `BottomTabBar` components. The visual reference is the Home/Profile dark surfaces and restrained green accents. Keep variable-length names separate from metadata/action rows; preserve space for selection borders and avoid changing label weight on selection. The logger retains compact, consistently aligned numeric columns, while screen actions and icon buttons use larger targets. Calendar, analytics, and program management own their headers rather than stacking a root header above them.

Add UI within the relevant feature slice, calculations in core/models, orchestration in services/export, and persistence behind repository interfaces with both SQLite and test adapters as needed. [CODEMAP.md](CODEMAP.md) links representative implementations and their tests. Add significant architectural rationale to [DECISIONS.md](DECISIONS.md); historical proposals do not change these boundaries.

Use [VALIDATION.md](VALIDATION.md) for scoped tests, contract verification, full regression gates, and documentation checks. Mobile dev commands (working directory `mobile/`): `npm install`, `npm start`, `npm run android`, `npm run ios`, `npm run web`. The latter commands start Expo for the chosen target. Companion dashboard (working directory `companion/`): `.\.venv\Scripts\python.exe -m streamlit run src/ui/app.py`. See workspace READMEs for environment setup. Run platform/device checks when a change depends on native behavior; mocked unit tests cannot establish that behavior.
